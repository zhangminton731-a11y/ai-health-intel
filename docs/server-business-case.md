# 企业为什么、何时需要服务端

核查日期：2026-10-04。当前决定：执行 A，保留 GitHub Pages；本文件不是服务器采购单。

## 决策结论

现阶段先把公开信息流的质量和更新可信度做好。服务端最有价值的升级是：持续采集与故障恢复、多人内容运营、按客户需求提供订阅与服务。服务器提供运行条件，具体功能仍要开发；换主机本身不会增加读者、线索或订单。

GitHub Pages 已经运行在 GitHub 的服务器上。真正的差别是我们是否拥有可持续执行任务、保存业务状态并处理用户请求的后端。后端既可以是云主机，也可以是托管数据库、队列或函数服务，不必把所有东西放到一台机器上。

## 能力与企业效益

| 维度 | 当前 Pages + Actions | 增加服务端并实现相应功能后 | 企业效益与验收指标 |
|---|---|---|---|
| 信息时效 | 定时批量生成，调度可能延迟；前台读取最近成功静态版本 | 不同信源不同频率，队列重试、优先级、积压追踪；仍受源站限流影响 | 重要政策/论文/竞品变化更快被发现；测源站发布到入库、入库到发布的 P50/P95 延迟 |
| 内容生产 | 单次任务负责整批处理；A 已能并发、缓存、诊断 | 采集、摘要、筛选、聚类任务分开扩容，崩溃后续跑，失败不反复付模型费 | 少等待、少重复处理；测每千条成本、失败恢复时间、积压最老任务年龄 |
| 信源扩张 | 没有“最多 17 个”的平台限制；取决于程序、Actions 时长、源站配额、审核质量 | 持久化游标、分布式 worker、独立调度，支持需长期状态的授权接口 | 新领域能以可控成本接入；测有效且不重复的内容增量，不以信源数量作为价值 |
| 多人运营 | 通过代码/文件协作，缺少业务审核后台 | 编辑待审池、角色权限、纠错撤回、操作记录 | 减少研发介入和重复确认；测单条编辑工时、误发率、撤回同步时间 |
| 用户服务 | 公共页面、分享、RSS、静态 API 和外部联系入口已可触达用户 | 用户主动订阅、偏好保存、跨设备收藏、个性化提醒、客户专属看板 | 从一次浏览变成持续服务；测订阅率、4 周留存、打开率、退订率 |
| 企业合作 | 用户看到内容后自行联系，渠道归因有限 | 同意后提交需求、进入 CRM、负责人跟进、记录结果 | 降低咨询流失，证明内容渠道贡献；测有效线索数、响应时间、商机与签约转化 |
| 数据资产 | 文件和有限历史窗口，适合公开阅读 | 可检索的多年事件、实体、证据与客户服务记录，权限隔离 | 更快准备客户研究和行业报告；测检索工时与报告交付周期 |

其中摘要、分类、去重、公共订阅链接、SEO、静态页面优化等并非服务端独占，A 路线也能继续改进。CRM、邮件、监控等还可以接托管服务；不要把“需要后端能力”误等同于“必须自购并维护服务器”。

## 稳定性要分两层

1. **网站可打开**：静态 Pages 即使采集失败仍能显示上一版；自管单机有宕机、磁盘、数据库和升级风险，不天然更稳定。前端继续静态托管、后端单独运行通常是可选路径。
2. **信息按目标时间更新**：Actions 的 schedule 可能延迟，高负载时排队任务可能被丢弃。自有/托管调度能增加补跑、重试和独立监控控制，但仍需备份恢复、告警、值班责任和外部探测，不能承诺零故障。

当前代码证明了两者不同：网站和采集正常，但筛选漏掉了 10 月 3 日论文。服务器无法自动修正这类内容规则错误。

## 信源上限如何估算

不能仅凭“买服务器”承诺从 17 个变成 1000 个。需要同时记录每个来源的耗时、限流、内容新增量、摘要成本和有效产出。

示例，仅说明算量：100 个源每 15 分钟检查一次，就是每日 9,600 次列表检查；不是 9,600 篇新文章。若全天只有 200 篇新增，摘要/模型处理应只针对新增或修订内容。源站检查、正文读取、模型费用和人工审核分别计量。缓存与增量处理在 Pages + Actions 上同样有用。

服务端提高的是调度与积压管理能力；无法赋予付费数据库、微信、小红书或其他平台的访问权限，也不能消除机器人限制。扩源还需要相应 API、许可或合法公开入口。

## 能链接到哪些人

- A 路线已可服务公开读者：临床科研人员、医院科研管理者、医疗 AI 产品团队、消费健康企业及合作机构；人群主要由内容定位和分发渠道决定。
- 服务端增加的是关系深度：课题组的研究方向订阅、企业竞品/政策看板、客户团队的共享收藏和定制情报。
- 付费客户门户、自动咨询分发、持续交付报告属于后续产品开发，不是 AIHOT 开源部署后自然获得的功能。
- 读者增长仍需要内容质量、专业社群、搜索收录和合作分发。中国大陆/海外的访问体验需按目标用户实测；换到海外云主机也不自动解决地域网络问题。

## 投资回报怎么向老板证明

建议先记录 2–4 周基线：更新延迟、每周维护小时、有效内容比例、订阅复访、合格合作线索。并行选一个明确付费方或内部使用方测试。

可直接使用的算式：

月净收益 = 节省工时 × 企业认可的小时成本 + 可归因新增业务毛利 − 云资源 − 数据/模型/API − 运维 − 开发摊销。

示例而非本项目实绩：2 人每天各节省 15 分钟、每月 22 个工作日，共节省 11 小时；若内部折算为 100 元/小时，则工时价值约 1,100 元/月。后端总月成本若超过这个数字，需要额外业务收益才能支撑，不能只看主机促销价格。

建议在以下任一需求已经被客户或内部团队确认时，再做服务端试点：

1. 明确需要小时内或更短延迟的提醒，并愿意为时效付费/配置值班。
2. 多人持续审核与纠错，文件协作已经造成可测量的工作损耗。
3. 存在订阅、客户专属空间、需求留资或 CRM 对接的真实使用需求。
4. 扩源后处理积压已成为瓶颈，缓存和并发优化仍不能满足目标。

## 已核对的官方边界

- [GitHub Pages 是静态托管](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)：不直接运行常驻数据库、业务 API 或 worker。
- [Actions schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)：计划任务可能延迟或被丢弃；公开仓库 60 天无活动可能停用计划任务。不能把当前 cron 表等同于时效 SLA。
- [Pages 限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)：发布站点最大 1 GB、月带宽软限制 100 GB；10 次/小时的构建软限制不适用于自定义 Actions 工作流。GitHub 不允许将 Pages 主要用于电商交易或商业 SaaS；未来客户服务平台不能简单照搬当前部署方式。
- [AIHOT 架构](https://github.com/KKKKhazix/AIHOT/blob/9848e936106db037d99a304887c36aad3fd0fad4/docs/architecture.md)：API、worker、web 三进程，统一公开读取层，付费请求回执与预算控制。其线上性能宣传不构成本项目的性能承诺。
