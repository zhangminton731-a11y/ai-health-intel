# RSS 故障诊断、重试与监控回执

## 问题与处理范围

2026-10-02 15:01 北京的线上批次中，npj Digital Medicine 和 Nature Biomedical Engineering 出现 XML 解析错误。此前只记录错误行列，无法区分当时返回的是损坏 XML、HTML 页面还是网络错误。本次从 main `67708def57` 开始修复。

RSS 采集继续使用 Python 标准库、现有来源地址和筛选规则。没有增加 LLM、浏览器采集或新信源。失败来源没有数据进入本轮推荐，不用历史条目补足数量。

## 采集行为

- 每个 RSS 最多尝试 3 次，运输与解析共用重试预算；单次网络超时 20 秒，响应上限 5 MiB。
- 临时失败间隔为 5、10 秒，各加 0–1 秒随机延迟。404 等非临时 HTTP 错误不重试。
- 429、408、5xx 可重试；`Retry-After` 支持秒数和 HTTP 日期。要求等待超过 60 秒时结束本轮请求，保存最早重试时间；后续批次在该时间前跳过请求，仍标记来源异常，不增加实际失败次数。
- 区分 `timeout`、`network_error`、`rate_limited`、`server_error`、`http_error`、`non_feed`、`invalid_xml` 和 `response_too_large`。
- RSS、Atom 和 Nature 的 RSS 1.0/RDF 继续按原字段提取。HTTP 200 的 HTML 或非订阅文档不会记作零条成功。

`source_health.json` 中每个来源的 `checks` 新增逐次请求信息：尝试序号、HTTP 状态、媒体类型、去掉账号/查询参数/片段的最终 URL、读取字节数、耗时、返回类型、错误类别及必要的解析行列。没有响应正文、原始异常消息、cookies 或完整请求/响应头。

每个来源新增 `last_success_at`、`consecutive_failures`、`last_checked_at`、`recovered`。首次上线没有历史时，最后成功时间为 null；成功及正常零更新会清零失败计数，停用或离线跳过不新增观察。连续计数按实际采集批次，不按单次 HTTP 重试计数。

## 状态与诊断保存

采集器将健康历史保存在 `output/.state/source_health_history.json`。main 工作流使用独立的 Actions cache 恢复与保存，即使采集退出失败、网站没有发布，也保留已完成采集的观察状态。当前批次健康文件另存为 14 天保留的 Actions artifact，不包含原始响应正文。

缓存是运行态，可能被平台清理；缓存缺失时从新观察开始计数，不声称历史连续性。整个进程中断且尚未写出健康文件时，不把上次 checkout 留存的健康文件当成本轮诊断。现有发布质量门、失败保留旧站的行为保持不变。

## 公网监控与飞书

公网监控仍读取已部署的 `api/v1/health.json`，而不是用未发布批次冒充线上健康。发现异常仍返回失败退出码。

通知规则：

1. 首次观察到异常时尝试发送；来源、错误类型变化，或达到连续 3 个采集批次失败时再次通知。
2. 同一异常在确认送达后 24 小时内不重复发送，超过 24 小时仍异常则提醒。
3. 已通知异常恢复正常后发送一次恢复消息。
4. 机器人未配置、发送失败或未获服务端成功确认，都不写成功回执；后续检查会继续尝试。

回执仅含状态、异常指纹和成功送达时间，保存在 `.monitor-state/receipt.json`，由 main 工作流独立缓存；不进入 Git 或网站。缓存丢失可能产生一次重复通知。监控去重不改变采集/部署失败工作流原有的失败通知。

### 仓库负责人需要配置

沿用现有 GitHub Actions secrets：`FEISHU_BOT_WEBHOOK`，以及启用签名时的 `FEISHU_BOT_SECRET`。本次没有读取、复制或替换凭据，也没有发送真实飞书消息。协作账号有代码推送权限，但不具备仓库管理权限；配置仍由仓库负责人完成。

配置后需检查一次真实异常通知、相同异常抑制和恢复通知；不能以模拟测试代替实际送达。该工作流只在 main 上发送通知。
